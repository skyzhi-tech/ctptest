# CTP 测试常见错误与 exsdk 接入边界

[项目首页](../README.md) · [快速开始](quickstart.md) · [CTP 程序化交易测试指南](ctp-testing.md)

先核对请求来源与真实回报，再判断是否满足目标场景。ctptest 不根据错误原因猜测错误码，也不把“请求已提交”当成测试通过。

## 为什么“开始”不可用，或一直在连接

SDK 登录、同步及交易日尚未就绪时，“开始”保持禁用。检查底部连接提示、交易前置、BrokerID、UserID、Password、AppID、AuthCode，以及官网 Token 的权益和绑定账号。连接异常保留原始原因，不能以空快照代替 READY。

Token 请通过 [易行量化官网](https://skyzhi.com/login?utm_source=github&utm_medium=docs&utm_campaign=ctptest&utm_content=token) 获取。接入字段及步骤见 [exsdk 快速开始](https://skyzhi.com/docs/quickstart?utm_source=github&utm_medium=docs&utm_campaign=ctptest&utm_content=quickstart)。

## 本地拒绝与柜台拒绝有什么区别

| 来源 | 含义 | 测试中如何处理 |
| --- | --- | --- |
| ctptest 本地校验 | 统一入口或专门的指令检查阻止请求 | 本地检查须有未调用 SDK 的证据，不能替代柜台错误 |
| `TradingResult.message` | SDK 即时拒绝或提交说明 | 明确未发送的不计请求数，不算柜台异步拒单 |
| `Order.status_msg` | 关联委托的柜台状态及拒单原文 | 保留原文、委托关联及能明确识别的错误码 |
| `Order.cancel_error` | 撤单失败原因 | 不把撤单提交当成撤单成功 |
| SDK 异常原文 | 连接、更新或运行失败 | 保留实际原因，结果按对应边界处理 |

SDK 数据由持续更新的快照读取，可能略过中间状态。日志里的 CTP 相关字段仅展示实际取得的值，不声称保存了每一次原始 CTP 回调。需要逐条原始回调审计时，须由 SDK 提供相应有序事件能力。

## CTP 错误码如何核验

当前适配读取文本中明确标注为 `错误码`、`ErrorID`、`error_code` 或 `返回码` 的整数，支持冒号、等号及空格等分隔。保留完整原文；没有明确标签、多个码值冲突或格式无法识别时，不从文字推导码值。

资金不足、持仓不足、市场状态错误须收到关联委托的目标拒单与明确非零码值，配置预期码时还须匹配。只有目标原文、没有可识别码值时为“结果待核对”。拆单须所有子单满足要求，其他拒单原因不能算通过。

完整字段含义与错误约定参见 [exsdk 错误处理](https://skyzhi.com/docs/errors?utm_source=github&utm_medium=docs&utm_campaign=ctptest&utm_content=errors) 和 [订单文档](https://skyzhi.com/docs/orders?utm_source=github&utm_medium=docs&utm_campaign=ctptest&utm_content=orders)。

## 资金不足测试为何没有通过

默认数量为 100 手，可在“配置 → 测试场景 → 资金不足委托手数”中调整，保存后无需重连。数量变大不保证触发资金不足：可用资金、合约保证金、SDK 检查及柜台规则均会影响结果。超过单笔数量上限而被拒绝，也不等于资金不足。

该测试按配置发送请求，不循环加仓或自动耗尽资金。柜台接受挂单且等待期内没有目标错误时显示“待环境准备”，挂单仍然保留；请核对实际委托，必要时明确使用“单笔撤单”处理。

## 持仓不足测试为何显示 SDK 限制

测试直接按账号快照中的可平多仓加一发送卖平；没有该合约持仓时使用零作为基数，不先开仓。若可平数量未知，先准备环境。

上期所或能源中心的 CLOSE 拆单、持仓检查可能在 SDK 内提前阻止超量平仓。实际发生该类本地拒绝时，保留 `TradingResult.message` 并标为“SDK 限制”，不能冒充柜台持仓不足回报。

此场景需要 SDK 公开支持让专用测试请求到达柜台的接口，或使用可触发目标柜台拒单的合约与环境。ctptest 不调用私有接口绕过检查，也不以其他错误代替目标错误。

## 市场状态错误为何没有触发

非交易时段不等于无法登录。柜台需要能连接并明确返回目标市场状态错误；登录失败、等待超时或收到其他拒单均不能算通过。

匹配包含“产品不在可以交易的阶段”等市场状态原文，码值只从实际回报中读取。若委托被正常接受，说明此次未取得目标错误，应按真实状态准备环境，而非仅根据本机时间判断通过。

## 买卖价格被柜台拒绝怎么办

ctptest 不订阅行情，也不检查盘口、新鲜度或涨跌停范围。普通报单直接使用用户买入价／卖出价，SDK 和柜台仍可能拒绝。日志保留实际 `LimitPrice`、错误码及 `StatusMsg`；需要修正价格时，在配置中保存后重新执行，不会自动改价重发。

仅“错误合约拦截”“最小价位拦截”“最大手数拦截”专门查询静态合约规则，并验证 ctptest 本地阻止请求。规则缺失时为待环境准备。

## 按钮恢复“开始”，为什么还没有结论

开平仓提交后在后台“等待成交”，柜台错误测试提交后在后台“等待回报”，不占用前台操作按钮。恢复“开始”仅表示当前发送步骤已完成；再次点击会产生新的测试请求。

开平仓双向全部成交才通过。单边成交、拒单、撤单或未确认状态按实际回报处理。回报超时只结束判定，已发委托后续状态仍写入原日志，不自动重发。

`UNKNOWN` 表示发送结果不确定，不能假设未发送。清理流程不会为未知撤单自动重复请求。详情见 [委托与停止规则](ctp-testing.md#委托与停止规则)。

## 断线测试、日志和凭据问题

- 断线告警使用外部真实断网及 SDK 发布的连接状态；有限更新等待超时不等于断线。检测时长由 SDK 和网络条件决定。
- 恢复测试要求同一会话已有断线记录；待 SDK 恢复并重新同步后核对结果。
- 日志测试列出缺少的前置测试，不会自动发送整组交易；重开工具清空记录，原材料须提前另存。
- 日志写入失败会禁止新的开平仓。请检查日志目录权限和磁盘空间，不要在运行中删除数据库或同时启动同配置的多个实例。
- 密码、Token、AuthCode 通过 Windows 凭据管理器读取，不使用明文回退。更换电脑后应重新通过 GUI 配置凭据；单独复制 TOML 不会迁移凭据内容。

## 历史现象与当前版本分开核对

早期 exsdk 1.7 运行曾出现 `ExError: 持仓查询包含 SDK 不支持的合约类别`。该信息是历史现象，不能据此认定升级后的版本仍有此问题或已经修复。若当前实际出现此异常，保留原文及版本，向 SDK 维护方提供可复现的合约类别信息；不能通过忽略持仓错误伪造同步成功。

项目不限定 exsdk 版本，更换版本后应重新核对自己的柜台场景。真实验收以 [检查表](../ACCEPTANCE.md) 中实际取得的证据为准；替身测试与构建检查不能证明柜台验收通过。
